# AI 早报运行说明

## 顺序与投递记录

Daily 工作流保持北京时间每日 05:37 的计划。GitHub 的定时任务可能延迟。

1. 运行回归测试，生成早报，并写入 `archive/YYYY-MM-DD.md` 和 `.status.json`。
2. 把归档提交到 main。推送失败时不发送通知。
3. 给每个已配置通知渠道写入投递预约，提交到 main。
4. 邮件和 Telegram 独立发送，分别保存结果。任一渠道失败不会阻止另一渠道。
5. 无论通知是否成功都尝试提交最终状态，并上传归档备份 artifact。

同一天重跑复用已有归档，不重新发送有投递记录的渠道。预约在通知前持久化，保证进程中断、读取超时或人工重跑时优先避免重复，而不是保证必达。

- `sent`：邮件服务器接受，或 Telegram 返回消息 ID。不是收件人已读证明。
- `failed`：明确未成功，例如 Telegram 403、429 超过等待限制或连接超时重试耗尽。
- `unknown`：可能已发送，或预约后运行中断。先核对邮箱/Telegram，不能直接重跑假设可补发。

未知、失败记录不会自动重发。若确认需要补发，先核对目标渠道和历史投递，再单独批准有针对性的恢复；不要删除整个当日状态文件。长 Telegram 报告可能已经发送部分分段，状态中保留已确认消息 ID。

Telegram 最多尝试 3 次，只重试连接建立超时或明确的 429 拒绝，单次 `retry_after` 最多 30 秒。读取超时、断线、5xx 和无有效回执都不自动重发。仅明确的 HTML 格式拒绝可改用纯文本。

## 手动验证

Actions → AI News Bot - Daily → Run workflow。默认 `dry_run=true`，仅抓取、生成与归档。需要真实推送时取消勾选；仍沿用仓库已有收件渠道。同日先 dry run 后真实运行会发送已归档的同一份报告。

本地：`pip install -r requirements.txt`，`python -m unittest discover -v`。
`python main.py --dry-run` 不发送。`python main.py` 会使用已配置渠道；本地的投递记录只保存在本地，不具备工作流的远程预约保障，不要从多个本地副本并发发送。

## 信息源诊断

状态 JSON、Actions Summary 和早报末尾展示各源数量及 `ok / empty / failed / partial / skipped`。`empty` 表示源可读取但当前窗口没有合格内容；`partial` 表示部分端点失败但备用来源可用；不把“不可读取”表述成“没有更新”。

RSS 每次尝试保留端点、HTTP 状态及分类错误，不保存响应正文、请求头或密钥。Jina 403 只证明拒绝访问；可能涉及服务策略、来源限制或认证，不能据此认定是限速，也不保证添加 API key 可以修复。可选的既有 `JINA_API_KEY` 现在可由 Actions secret 注入，但不会自行创建或购买密钥。

2026-11-03 历史日志显示 7 个 X 账号 RSS 失败且 Jina 返回 403。此次修改增强识别与可见性，没有绕过访问限制，也未验证这些外部来源已恢复。官方博客/Claude Code 发布记录仍独立抓取。源失败不再中断其他来源；全部无可用内容时工作流失败，不声称稍后会自动重试。

## 当天未运行的提醒（尚未启用）

独立检查应在北京时间约 09:00 查询 Daily 的最新运行与当日 `.status.json`，区分未启动、生成失败、仍在运行和部分投递。监控必须独立于 Daily，否则 Daily 禁用时也无法报警。

在确认提醒接收渠道前，不新增提醒收件人、第三方服务或定时外发。当前 Actions 失败状态/summary 已可查看，但它们不能发现完全没有启动的 Daily。
